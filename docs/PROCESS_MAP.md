# Process map

Every process found in the code and in the work it describes: its states, what moves it
from one to the next, what goes in and comes out, and who acts. Each is ranked by what
it is worth to someone running a real estate firm. The top four are built: their states
and transitions are data in `lib/engine/processes.ts`, their records persist in the
firm folder, and every action is a command and an MCP tool. The rest are mapped as they
were found, so the next one can be built without re-reading the code.

"Who" is one of: **agent** (an AI agent can do it), **person** (only a person may), or
**either**. Mapped 2026-11-12.

## Ranking

| # | Process | Worth to an operator | State today |
|---|---|---|---|
| 1 | Run a playbook | Everything else rides on it: the order of work, who does each step, what needs approval, and proof that it was done | **Built** |
| 2 | Audit a firm | Finds what an existing firm is missing before a lender, an investor or the state does | **Built** |
| 3 | Track deadlines | A missed filing costs money or standing; a calendar file is useful the day it is made | **Built** |
| 4 | Move a deal from screen to close | The daily work of an acquisitions shop; six playbooks in a row with go or no-go points between them | **Built** |
| 5 | Respond to a situation | Rare, but the clock is in hours or days | Mapped. A situation can be run as a playbook; the clock is not kept |
| 6 | Raise capital for an offering | High value while a raise is open; one record per investor | Mapped. Offerings and investors can be subjects; no offering-level state |
| 7 | Keep the firm's records | Decisions, documents and the entity's own status | Mapped. The folder is created, checked and backed up, and decisions have commands (they came with process 4); the profile and the documents are still edited by hand |
| 8 | Keep the catalog honest | Serves whoever writes the playbooks, not the operator | Mapped. Mostly explicit already, as validators and review ledgers |

Ranking rule: what a working operator would miss first if it were gone. Processes 1 to 3
came first because 2 and 3 produce something useful on an existing firm in one sitting,
and both need 1 underneath them. Process 4 followed because it is mostly a view over runs
that already existed: a deal's stage is worked out from its playbooks, and only the
decision to go on or to drop is new.

### Run a playbook

Work a playbook step by step for the firm or for one deal: see what is next, who does it, what needs approval, and record each step with its proof.

Commands: `pcre run …`, `pcre subject …`. Guide: `docs/guides/run-a-playbook.md`.

#### Playbook run (`run`)

One playbook worked through for the firm, or for one of its subjects (a deal, an offering, an investor). Kept in `progress.json: playbooks.<playbook>, or subjects.<subject>.playbooks.<playbook>`; its state is worked out from those records each time, never stored.

| State | Meaning |
|---|---|
| `not-started` (start) | No run of this playbook exists yet. |
| `open` | Started. At least one step that applies is still to do or blocked. |
| `complete` | Every step that applies is done, skipped or not applicable. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `start` | `not-started` | `open` | either | `playbook-is-written` |
| `approve` | `open` | `open` | person | — |
| `complete` | `open` | `complete` | the engine, by itself | `every-step-resolved` |
| `resume` | `complete` | `open` | the engine, by itself | — |

#### Step (`step`)

One step of a run. Kept in `progress.json: the run's steps.<step>`.

| State | Meaning |
|---|---|
| `todo` (start) | Not done yet. |
| `done` | Done, with the date, who did it and where the proof is. |
| `blocked` | Waiting on someone or something; the note says what. |
| `skipped` | A person chose not to do it; the note says why. |
| `not-applicable` | It does not fit this firm; the note says why. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `done` | `todo`, `blocked` | `done` | either | `predecessors-resolved`, `person-for-human-step`, `approval-recorded` |
| `block` | `todo` | `blocked` | either | a note |
| `unblock` | `blocked` | `todo` | either | — |
| `skip` | `todo`, `blocked` | `skipped` | person | a note |
| `not-applicable` | `todo`, `blocked` | `not-applicable` | either | a note |
| `reopen` | `done`, `skipped`, `not-applicable` | `todo` | either | a note |

#### Subject (`subject`)

Something the firm runs playbooks for more than once: a deal, an offering, an investor, a property. Kept in `progress.json: subjects.<subject>`.

| State | Meaning |
|---|---|
| `open` (start) | Active. Runs can be started and worked for it. |
| `closed` | Finished or dropped. Its runs stay on record. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `close` | `open` | `closed` | either | a note |
| `reopen` | `closed` | `open` | either | a note |

### Audit a firm

Check a firm that already exists against an audit playbook: record each check as clear, a finding or unverified, then get the score, the findings and a sheet for each person who has something to fix.

Commands: `pcre audit …`, `pcre finding …`. Guide: `docs/guides/audit-a-firm.md`.

#### Audit (`audit`)

One pass through an audit playbook's checks, for a firm that already exists. Kept in `audits.json: audits[]`.

| State | Meaning |
|---|---|
| `open` (start) | Checks are being recorded. |
| `closed` | Every check that applies has an outcome. Findings may still be open. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `approve-lookups` | `open` | `open` | person | — |
| `close` | `open` | `closed` | either | `every-check-recorded` |
| `reopen` | `closed` | `open` | either | a note |

#### Check (`check`)

One check of an audit. A check records what is true; it never fixes anything. Kept in `audits.json: the audit's checks.<check>`.

| State | Meaning |
|---|---|
| `unchecked` (start) | Not looked at yet. |
| `clear` | Verified, with where the proof is. |
| `finding` | Something is wrong or missing. A finding is opened for it. |
| `unverified` | Could not be confirmed. It never counts as clear. |
| `not-applicable` | It does not fit this firm; the note says why. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `clear` | `unchecked`, `unverified`, `finding`, `not-applicable` | `clear` | either | `earlier-checks-recorded`, `lookups-approved`, `person-for-human-check`, `no-open-findings` |
| `finding` | `unchecked`, `clear`, `unverified`, `not-applicable` | `finding` | either | `earlier-checks-recorded`, `lookups-approved` |
| `unverified` | `unchecked`, `clear`, `finding`, `not-applicable` | `unverified` | either | a note, `earlier-checks-recorded`, `no-open-findings` |
| `not-applicable` | `unchecked`, `clear`, `finding`, `unverified` | `not-applicable` | either | a note, `no-open-findings` |

#### Finding (`finding`)

One thing an audit found wrong or missing, with who fixes it and by when. Kept in `audits.json: the audit's findings[]`.

| State | Meaning |
|---|---|
| `open` (start) | Not fixed yet. |
| `fixed` | Fixed; the note says where the proof is. |
| `accepted` | A person chose to live with it; the note says why. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `fix` | `open` | `fixed` | either | a note |
| `accept` | `open` | `accepted` | person | a note |
| `reopen` | `fixed`, `accepted` | `open` | either | a note |

### Track deadlines

Keep the firm's dated duties in one calendar: add them by hand or from the deadline calculator, see what is overdue or due soon, and export a calendar file.

Commands: `pcre deadline …`. Guide: `docs/guides/track-deadlines.md`.

#### Deadline (`deadline`)

One dated duty. Overdue, due soon and upcoming are worked out from the date each time; they are not stored. Kept in `calendar.json: items[]`.

| State | Meaning |
|---|---|
| `open` (start) | Still to be met. |
| `done` | Met; the record says when and by whom. |
| `dismissed` | A person decided it does not apply; the note says why. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `done` | `open` | `done` | either | — |
| `dismiss` | `open` | `dismissed` | person | a note |
| `reopen` | `done`, `dismissed` | `open` | either | a note |

### Move a deal from screen to close

Take one deal through the acquisition playbooks in order: see every deal's stage, record each decision to go on or to drop, and start the next playbook when a person says go.

Commands: `pcre deal …`, `pcre decision …`. Guide: `docs/guides/move-a-deal.md`.

#### Deal (`deal`)

A deal moving through the acquisition playbooks in order. A deal is a subject of kind deal. Its stage is the first acquisition playbook it has not finished, worked out from its runs each time. Kept in `progress.json: subjects.<deal> (closedOn and outcome); decisions.json holds each decision to go on or to drop`.

| State | Meaning |
|---|---|
| `active` (start) | Being worked. Its stage is the first acquisition playbook not yet complete. |
| `completed` | Bought: every acquisition playbook is complete and the deal is closed. |
| `dropped` | A person decided not to go on; the decision and the reason are on record. |

| Action | From | To | Who | Needs |
|---|---|---|---|---|
| `advance` | `active` | `active` | person | a note, `stage-complete`, `next-playbook-written` |
| `drop` | `active` | `dropped` | person | a note |
| `complete` | `active` | `completed` | either | `track-complete` |
| `reopen` | `completed`, `dropped` | `active` | either | a note |

### What can refuse a move

| Guard | Meaning |
|---|---|
| `playbook-is-written` | The playbook is written at full depth. An outline has no steps to run. |
| `predecessors-resolved` | Every step this one comes after is done, skipped or not applicable. |
| `person-for-human-step` | A step marked human is recorded in a person's name, never the agent's. The agent hands it over and records it once the person says it is done; the name is its word, not proof. |
| `approval-recorded` | A step that needs approval names the person who approved it: each time for every-run, once per run for standing. A signature step is recorded in the signer's name. The agent asks first and gives a name only after that person says yes. |
| `every-step-resolved` | Every step that applies is done, skipped or not applicable. |
| `earlier-checks-recorded` | Every check this one comes after has an outcome. |
| `person-for-human-check` | A human check is recorded as clear only in a person's name, once that person says it is clear. An agent may record it as a finding or as unverified. |
| `lookups-approved` | Before an agent records a check that reads a public record, a lookup approval for this audit is recorded in a person's name, once that person says yes. |
| `no-open-findings` | The check has no open finding. Fix or accept the finding first. |
| `every-check-recorded` | Every check that applies has an outcome. |
| `stage-complete` | The deal's current acquisition playbook is complete: every step that applies is done, skipped or not applicable. |
| `next-playbook-written` | The next acquisition playbook is written at full depth for this deal's structure. |
| `track-complete` | Every acquisition playbook in the track is complete for this deal. |

### Inputs, outputs and decision points

| Process | Goes in | Comes out | Where a person decides |
|---|---|---|---|
| Run a playbook | A playbook from the catalog; the firm's structure, property type and jurisdictions; for each step, who did it and where the proof is | `progress.json` with every step's state; the log; the next steps that are ready | Skipping a step; approving a step marked `every-run` or `signature`; the one standing approval per run; every human step |
| Audit a firm | An audit playbook; the firm's documents; public records, once a person has approved lookups | `audits.json`: each check's outcome and evidence, the findings, the score; `audit/<id>/findings.md` and a sheet for each person with something to fix | Approving public-record lookups; recording a human check as clear; accepting a finding instead of fixing it |
| Track deadlines | Dates typed by hand; dates the deadline calculator works out from a rule card | `calendar.json`; what is overdue and due soon; a calendar file to import | Dismissing a deadline; relying on a computed date (each is marked for review) |
| Move a deal | A deal's name; the acquisition playbooks in catalog order; the runs worked for that deal | Each deal's stage; the track with every playbook's state; `decisions.json` with each decision to go on or to drop | Going on to the next playbook; dropping the deal; every signature inside the playbooks |

## Mapped, not built

These are written as they were found. None of them is in `processes.ts` yet, so their
states below are a reading of the code and the work, not a contract.

### What process 4 still lacks

It is built as found in the catalog: a deal's stage is the first acquisition playbook it
has not finished, so the stages carry the playbooks' own titles and not the trade's
words (screening, under contract, in diligence). Two things are not done. Contract-period
deadlines are not added by themselves when the effective date is recorded; they are added
with `pcre deadline compute --subject <deal>`. And the decisions inside a playbook (waive
or extend diligence, accept a lender's retrade) are steps of that playbook, not entries
in the decision log.

### 5. Respond to a situation

Found in: the 22 situation records (`trigger`, `urgency` of hours, days or weeks) and the
connector's `match_situation`.

| State | Reached when | Who |
|---|---|---|
| `noticed` | Something happens; it is described in plain words | either |
| `matched` | The closest situation is chosen, or none fits | agent proposes, person confirms |
| `responding` | The situation's steps are being worked | either, step by step |
| `resolved` | Every step is resolved, or a person closes it | person |

Inputs: what happened and when. Outputs: the steps taken with proof, and any deadline the
situation creates. Missing: the time it was noticed, a response clock measured against the
urgency, and a link from a situation back to the run or deal it interrupted.

### 6. Raise capital for an offering

Found in: the six stand-up and raise playbooks, the Form D and state notice deadlines, and
the investor steps in "Onboard an investor" and "Call capital and fund a closing".

| Record | States | Who |
|---|---|---|
| Offering | `planning` → `open` → `first-close` → `final-close` → `closed` | person decides each move; counsel on the exemption |
| Investor, per offering | `prospect` → `questionnaire-in` → `verified` → `subscribed` → `funded`, or `declined` | agent prepares and checks; the investor and a principal sign |
| Capital call | `noticed` → `partly-funded` → `funded`, or `defaulted` | agent prepares the notice; a person sends it and confirms funds |

Inputs: the exemption chosen, the offering documents, each investor's answers. Outputs: the
investor register, the filings and their dates. Missing: offering-level state, the first
sale date flowing into the calendar by itself, and a register built from the investor runs.

### 7. Keep the firm's records

| Record | Found in | States or rule | Who |
|---|---|---|---|
| The entity | `firm.json`, `entity.status` | `not-started` → `filed` → `formed`; `formed` → `forfeited` → `formed` again on reinstatement; any → `terminated` | the state moves it; a person records it with proof |
| A decision | `decisions.json` | Appended, never edited: what was decided, by whom, when | person decides; either records |
| A document | `artifacts.json` | Expected (a playbook step produces it) → located (a path is recorded) → missing (known to exist, path unknown) | either |
| The folder | `pcre firm init`, `check`, `upgrade` | Created → valid → backed up | either |

Missing: commands for decisions and documents (they are edited by hand today), and a list of
documents the firm's finished steps should have produced but that are not on record.

### 8. Keep the catalog honest

| Process | Found in | States | Who |
|---|---|---|---|
| Write and review a playbook | `depth`, `review`, `content/reviews.json`, the validator | `outline` → `full`, AI-drafted → practitioner-reviewed (→ attorney-reviewed, unused) | agent drafts from primary sources; a practitioner approves; the validator refuses a chip with no dated approval |
| Keep a record current | `lastVerified`, `asOf`, the 180-day rule | current → `check date` → re-verified | agent re-reads the sources; a person approves a change to reviewed text |
| Check citations | `npm run citations`, `citations:live` | recorded → live-checked → blocked or broken | agent |
| Rank a vendor | `rankings/`, the `rank-*` commands | candidate → probed → collected, or untested → sealed → judged → stale when the evidence changes | agents collect and judge; no one works around a bot wall |
| Publish a market | the golden cells, `rank:calibrate` | calibrated at 18 of 20 → published → practitioner-reviewed | agent; a practitioner reviews |
| Contest a verdict | the issue template | filed → evidence re-collected → re-judged → answered | anyone files; agents re-judge |
| Test a host | `lib/hosts.ts` | documented → tested, with the date and what was run | a person runs the test with their own account |
| Guard against leaks | `tools/leakcheck`, the commit hook | every commit: checked → clean, or refused | automatic |
| Release | `docs/DEPLOY.md` | committed → pushed → deployed → public | the owner only |

Most of these are already explicit as validators and ledgers. What they lack is one place
that says what state each record is in and what is due next: a maintainer's `status`.

### Not a process

The four calculators (waterfall, debt sizing, returns, deadlines) take inputs and return
results with a formula trace. They keep no state, so there is nothing to resume. The
deadline calculator feeds process 3.
